## Проверки и границы работы

- Для каждого исправленного дефекта — узкая регрессионная проверка и проверка соседнего корректного сценария, когда это практически возможно.
- Для интеграций проверять полный путь: настройки → запрос → ответ → сохранение → интерфейс.
- Не отправлять платные или изменяющие чат запросы только ради проверки без согласованного тестового сценария.
- Тесты с подменённым API не считать проверкой реального провайдера или визуальной проверкой браузера.
- Перед передачей изменений использовать `caveman-review`; перед предложением коммита — `caveman-commit`.
- Отмечать в плане фактически выполненные проверки и оставшиеся ограничения.
- Не менять архитектуру целиком, правила начисления отношений или сохранённые данные ради сопутствующего улучшения.
